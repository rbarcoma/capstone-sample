## 1. Project scope

Quezon City Hall is the official beneficiary of this Laravel, React, Inertia.js, MySQL, and Python Decision Support System for Renewable Energy Transition. The original research used city-wide Quezon City electricity data. The immediate objective is to evaluate and improve the **existing forecasting system using actual historical electricity datasets supplied by Quezon City Hall**.

The source of the data does not change the product scope. **Do not convert this application into a building-specific or multi-building forecasting platform.** Do not introduce building management, building selectors, building dashboards, separate production models for each building, or building-identity schema expansion. The current workflow remains:

```
dataset upload → preprocessing → model training/evaluation → next-month prediction → Analytics and DSS
```

Treat one coherent consumption series as the active dataset for an experiment. If beneficiary files describe different series, evaluate them in separate, traceable test runs using the existing workflow; do not append unrelated observations into one series. This is an experimental data-integrity requirement, not a new building-management feature.

## 2. Development restrictions

- **Preserve the current UI and UX:** layouts, styling, navigation, components, tables, charts, and all visual design. Do not add screens or controls. Any later factual label or explanatory-text correction must be necessary for correctness, explicitly accounted for in the implementation scope, and preserve the existing design.
- Preserve Laravel, React, Inertia.js, MySQL, and Python. Reuse existing helpers and interfaces; avoid wholesale rewrites, unrelated refactors, and unnecessary schema changes.
- Do not fabricate beneficiary records, replace missing measurements with city-wide values, or modify actual observations to improve scores. Synthetic fixtures are permitted only in clearly identified software tests.
- Do not use future consumption, unavailable future weather/demand measurements, or evaluation outcomes as training information.
- Do not clip negative R², selectively remove difficult evaluation months, or substitute training scores for out-of-sample results. A high R² is not an acceptance requirement.
- Do not assume Random Forest or XGBoost will outperform simpler models. A well-evaluated baseline may be the most defensible forecast.
- Keep decision support rule-based and explainable. Do not infer investment or engineering readiness from unsupported inputs.
- Preserve unrelated local work and original datasets. Do not expose `.env` secrets or private beneficiary identifiers in logs or public artifacts.

### 3.2 Assessment baseline findings (confirmed before the Priority 2 implementation)

These describe the pre-change assessment. Current resolved/open status is tracked in `CURRENT.md`; do not repeat completed work from this historical list.

1. **Initial lags contain their own target.** `app/Support/EnergyPreprocessor.php:43-44` and the Python fallbacks at `Python/train_model.py:89-90` / `Python/predict_next_month.py:80-81` substitute the current consumption when earlier values are unavailable. Verified in the exported data: row 1 has `lag_1 == lag_2 == 226100.00` (its own target) and row 2 has `lag_2 == 251300.00` (its own target). This is invalid feature initialization and can distort fitting; it does not alone prove the cause of the exact negative R².
2. **Calendar gaps have inconsistent handling.** Lags use the preceding *row* rather than the verified preceding *calendar month*. Training trend uses row position (`Python/train_model.py:95`, `app/Support/EnergyPreprocessor.php:45`), while next-month prediction trend uses elapsed months (`Python/predict_next_month.py:118-125`). Gaps can produce mislabeled lags and different training/serving feature meanings. The inspected export is continuous, so this is a general defect rather than an established cause of this run's score.
3. **Missing values have inconsistent meanings.** Preprocessing substitutes zero for absent climate/demand values (`app/Support/EnergyPreprocessor.php:38-42`); the training and historical CSV readers convert blanks to zero (`Python/train_model.py:77`, `Python/predict_history.py:29`); the next-month reader skips invalid rows (`Python/predict_next_month.py:57-66`); upload validation rejects incomplete numeric data (`app/Http/Controllers/Admin/DataManagementController.php:248-257`). Missing, zero, estimated, and invalid values need an explicit, consistent policy.
4. **Evaluation does not reproduce forecast-time inputs.** Holdout/CV evaluate historical rows with the target month's *actual* weather and demand, while next-month prediction estimates those fields from a historical same-month or recent average (`Python/predict_next_month.py:130-147` — for 2026-09 this resolves to the single 2025-09 row). The actual target-month values would normally be unavailable at the forecast origin. Chronological sorting alone does not eliminate this leakage or the train/serve mismatch.
5. **The model is large relative to the sample.** 12 predictors plus an intercept (`Python/train_model.py:9-22`), 12 holdout training rows, and as few as 3 rows in the first CV fold. Year, month, and trend also contain overlapping time information. Overfitting, unstable coefficients, and sensitivity to particular months are plausible consequences requiring controlled tests.
6. **Resolved in source by Priority 5b (2026-10-23); retained as historical evidence.** The active algorithm was mislabeled: `Python/train_model.py:183,197-198` adds a fixed `0.1` penalty to the non-intercept diagonal, but the artifact reported `"model_type": "Linear Regression"` (`Python/train_model.py:205`). It is a regularized linear fit. The trainer/fallbacks/new copy now emit `Ridge (penalty 0.1)`; saved pre-5b forecast rows and dated report snapshots retain their original labels and are not retroactively rewritten. A separately tuned Ridge comparison remains not integrated. The standalone `Python/algo/train_random.py`, `train_xgboost.py`, and `compare_models.py` use a fixed legacy dataset path (`Python/qc_final_merged_dataset.csv`) and a different artifact interface; their selection does not automatically change the active application model.
7. **CV summaries can mislead.** Four of the five current folds contain one evaluation observation, for which the evaluator returns R² = 0 because target variance is zero (`Python/train_model.py:235`). The final fold has five observations. Averaging these R² values is not a meaningful overall R², and averaging unequal fold RMSEs is not pooled RMSE (`Python/train_model.py:280-282`). Existing chronological splitting and training-only standardization are useful and should be retained.
8. **Analytics mixes fitted values with saved forecasts.** The final production model is fitted on all available rows (`Python/train_model.py:356`), then `Python/predict_history.py` predicts those same rows. Analytics merges those in-sample refits with saved forecasts into one predicted series (`app/Http/Controllers/Admin/AnalyticsController.php:39,63-67`; `app/Http/Controllers/User/ViewerController.php:112,135-137`). This explains how the plotted curves can appear close while held-out performance is poor: the chart and the metrics represent different evaluation conditions. The clipped percentage-error complement shown as "accuracy" (`AnalyticsController.php:70-72`, `ViewerController.php:140-141`, `Python/predict_history.py:47-49`) is neither R² nor evidence of prospective performance, and it is floored at 0 so it can read positive even at R² = -7.77.
9. **Forecast provenance and cache identity are limited.** The workflow hashes the dataset but not feature-code/configuration versions (`app/Support/MlWorkflow.php:21,26,42-48`). Direct prediction checks model existence rather than independently enforcing a matching data hash (`app/Support/MlWorkflow.php:179-189`). Forecasts are upserted by period (`app/Support/MlWorkflow.php:101-114`), so a later run can replace an earlier result. Cached Analytics inputs and prior forecasts can also refer to a previous dataset experiment unless provenance is checked. Re-verified 2026-10-22 by direct reading: the artifact identity and state key are derived from the dataset hash and the feature signature only (`MlWorkflow.php:253-265`), so a change to `Python/train_model.py` does not invalidate the artifact; the trainer writes to the **final** artifact paths while the state already references them (`MlWorkflow.php:228-242`, `:79-84`), so a failed run can leave a partial artifact at the live path; the state file is written non-atomically (`MlWorkflow.php:44`) and records no trainer signature, training cutoff, or evaluation-protocol identifier. ### 3.3 Suspected causes to investigate (not conclusions)

Insufficient history, redundant features, consumption-pattern changes, outliers, billing/calendar misalignment, incorrect units, unverified billed-demand semantics, and future-context estimation error may contribute to poor performance. Compare residuals and controlled feature/model variants to determine their effects. Do not claim that a city-wide origin or a single code defect explains all errors, and do not claim a specific algorithm will fix them without evidence.

## 6. Documentation maintenance (required)

Three Markdown files in the project root form the project's documentation set. **Codex must maintain all three throughout development.**

| File | Role | Update trigger |
| --- | --- | --- |
| `AGENTS.md` | Project-wide guidelines: scope, restrictions, known problems, improvement plan, testing requirements, and this workflow. | Only when project-wide instructions or technical requirements change. |
| `CURRENT.md` | Live development status: phase, verified working features, open issues, pending tasks, in-progress tasks, completed tasks, next steps, blockers. | **After every meaningful development task.** |
| `IMPLEMENTATION.md` | Chronological history of completed technical changes with real evidence. | **After every completed implementation.** |

### 6.1 Before starting any development task

1. Read `AGENTS.md` in full.
2. Read `CURRENT.md` to learn the current phase, open issues, and what is already done.
3. Read the relevant sections of `IMPLEMENTATION.md` to understand what has already been implemented and tested.
4. Identify the current task and the existing implementation before editing anything.
5. Do not repeat completed work or introduce unrelated changes.

### 6.2 After completing a task

1. **Update `CURRENT.md`** so it reflects the actual project state: mark completed items `[x]`, move work in progress to `In Progress`, add newly discovered issues, and refresh priorities, next steps, and blockers.
2. **Append to `IMPLEMENTATION.md`** the actual changes and the actual test results. Use the entry template in §6.4.
3. **Update `AGENTS.md`** only when project-wide instructions or technical requirements change (new restriction, new plan priority, new testing requirement). Do not use `AGENTS.md` as a change log.
4. Keep all three files concise, accurate, and consistent with the source code.

### 6.3 Status markers

Use exactly these markers in `CURRENT.md`:

- `[x]` — Completed and verified (the change exists and the relevant check was run and passed).
- `[ ]` — Pending (not started).
- `In Progress` — Currently active task.
- `Blocked` — Requires additional data, credentials, or dependencies that are not yet available.

### 6.4 `IMPLEMENTATION.md` entry template

Every entry must contain, in order:

1. **Date and task name.**
2. **Problem identified.**
3. **Root cause**, if confirmed (write "Not confirmed" otherwise).
4. **Solution implemented.**
5. **Files created or modified** (paths, one per line).
6. **ML algorithms or forecasting logic affected.**
7. **Tests executed and their actual results** (paste the real command and its real output; never paraphrase into a claim).
8. **Remaining limitations or follow-up tasks.**

### 6.5 Honesty rules for documentation

- **Never** mark an implementation as completed unless the corresponding changes have actually been made.
- **Distinguish three states explicitly** — *Implemented* (code changed), *Tested* (a command was run), *Verified* (the command passed and the output was inspected). Use these words precisely.
- **Do not invent** test results, model accuracy improvements, or completed work. If a test was not run, say so.
- **Do not invent** a measured R², MAE, or RMSE. Only cite values that were produced by an actual run.
- Record the dataset hash, row counts, and evaluation periods alongside any metric so a number can always be traced to a specific experiment.
- If a claim cannot be verified with the current data or dependencies, mark it `Blocked` or list it under *Suspected causes* — never under verified findings.
